## Base Route

All category endpoints are mounted under:

- `/api/category/`

---

## Access Model

- Public users can read categories, skills, and sub-skills.
- Write operations (`POST`, `PUT`, `PATCH`, `DELETE`) require `is_staff=True`.
- API deletes are soft deletes (`is_delete=True`) for Category/Skill/SubSkill viewsets.

---

## Features

- Hierarchical taxonomy: Category → Skill → SubSkill
- Public read access with staff-only writes
- Soft-delete behavior in API deletes
- Search/filter/order support across all list endpoints
- Slim/full serializers via `fields=basic`
- Cached list/detail responses (300 seconds)
- Bulk import via `load_skills` management command

---

## Endpoints (Router)

These endpoints are generated by DRF `DefaultRouter`:

### Categories
- `GET /api/category/categories/`
- `POST /api/category/categories/` (staff only)
- `GET /api/category/categories/<uuid:id>/`
- `PUT /api/category/categories/<uuid:id>/` (staff only)
- `PATCH /api/category/categories/<uuid:id>/` (staff only)
- `DELETE /api/category/categories/<uuid:id>/` (staff only, soft delete)

**Lookup field**: `id` (UUID)

**List query params**
- `q`: search in `name` / `description`
- `parent`: filter by parent category UUID
- `is_featured`: boolean (`1|true|yes` or `0|false|no`)
- `is_active`: boolean (`1|true|yes` or `0|false|no`)
- `ordering`: comma list from `order,name,created_at,updated_at` (supports `-` prefix)
- `fields=basic`: uses slim category serializer
- pagination: `page`, `page_size` (default 20, max 100)

**Public filtering behavior**
- Non-staff only see categories with `is_delete=False` and `is_active=True`.

---

### Skills
- `GET /api/category/skills/`
- `POST /api/category/skills/` (staff only)
- `GET /api/category/skills/<uuid:pk>/`
- `PUT /api/category/skills/<uuid:pk>/` (staff only)
- `PATCH /api/category/skills/<uuid:pk>/` (staff only)
- `DELETE /api/category/skills/<uuid:pk>/` (staff only, soft delete)

**List query params**
- `q`: search in `name` / `description`
- `category_id`: filter by category UUID
- `is_active`: boolean
- `ordering`: comma list from `order,name,created_at,updated_at`
- `fields=basic`: slim serializer
- pagination: `page`, `page_size`

**Public filtering behavior**
- Non-staff only see skills where:
  - skill `is_delete=False`, `is_active=True`
  - parent category `is_delete=False`, `is_active=True`

---

### Sub-Skills
- `GET /api/category/sub-skills/`
- `POST /api/category/sub-skills/` (staff only)
- `GET /api/category/sub-skills/<uuid:pk>/`
- `PUT /api/category/sub-skills/<uuid:pk>/` (staff only)
- `PATCH /api/category/sub-skills/<uuid:pk>/` (staff only)
- `DELETE /api/category/sub-skills/<uuid:pk>/` (staff only, soft delete)

**List query params**
- `q`: search in `name` / `description`
- `skill_id`: filter by parent skill UUID
- `difficulty_level`: `beginner|intermediate|advanced|expert`
- `is_active`: boolean
- `ordering`: comma list from `order,name,created_at,updated_at`
- pagination: `page`, `page_size`

**Public filtering behavior**
- Non-staff only see sub-skills where sub-skill, parent skill, and parent category are all active and not soft-deleted.

## Serialization Shapes

### CategorySerializer fields
- `id`, `name`, `description`, `icon`, `parent`
- `is_active`, `is_featured`, `is_delete`, `order`
- `skill_count`, `technician_count`
- `created_at`, `updated_at`
- `skills` (nested full `SkillSerializer`)

### CategorySlimSerializer fields
- same top-level category fields
- `skills` uses `SkillSlimSerializer` (no nested `sub_skills`)

### SkillSerializer fields
- `id`, `category`, `name`, `description`
- `is_active`, `is_delete`, `order`
- `technician_count`
- `created_at`, `updated_at`
- `sub_skills` (nested `SubSkillSerializer`)

### SkillSlimSerializer fields
- same skill fields except no nested `sub_skills`

### SubSkillSerializer fields
- `id`, `skill`, `name`, `description`
- `difficulty_level`, `is_active`, `is_delete`, `order`
- `full_path`
- `created_at`, `updated_at`

## Data Model Summary

### Category
- Inherits `TimestampedModel` (`id`, `is_delete`, `created_at`, `updated_at`)
- Core fields: `name`, `description`, `icon`, `parent`, `is_active`, `is_featured`, `order`
- Computed helpers: `skill_count`, `technician_count`, `get_full_hierarchy()`

### Skill
- FK to `Category` via `category`
- Core fields: `name`, `description`, `is_active`, `order`
- Unique constraint: `(category, name)`
- Computed helper: `technician_count`

### SubSkill
- FK to `Skill` via `skill`
- Core fields: `name`, `description`, `difficulty_level`, `is_active`, `order`
- Unique constraint: `(skill, name)`
- Computed helpers: `technician_count`, `full_path`

## Caching & Pagination

- `list` and `retrieve` responses for all three viewsets are cached for 300 seconds.
- Pagination class defaults:
  - `page_size = 20`
  - `page_size_query_param = page_size`
  - `max_page_size = 100`

## Management Command

### Load Skills from JSON

Command:

- `python manage.py load_skills --file <path_to_json>`

Behavior:
- Resolves relative file paths from project root.
- Expects JSON root structure:
```json
{
  "category": "Category Name",
  "skills": [
    {
      "skill": "Skill Name",
      "sub_skills": ["Sub Skill A", "Sub Skill B"]
    }
  ]
}
```
- Uses get-or-create for `Category`, `Skill`, `SubSkill`.
- Defaults new records to active and sets display order based on array order.

Example:

- `python manage.py load_skills --file dependancy/skills_files/data_skills.json`

## Frontend Notes

- Use `/api/category/...` paths (not `/api/categories/...` legacy paths).
- For lightweight lists, use `fields=basic`.
- Treat delete operations as soft delete in API behavior.
- Query boolean filters with accepted values: `1`, `true`, `yes`, `0`, `false`, `no`.

---

## Frontend Implementation Guideline

- Load taxonomy progressively: categories first, then skills/sub-skills by selected IDs.
- Use `fields=basic` for list pages and full serializer only for details/forms.
- Keep filter state in query params (`q`, `category_id`, `skill_id`, etc.) for shareable URLs.
- Show admin editing controls only when current user is staff.
- Treat delete as soft-delete in UI messaging (not hard removal).
- Use pagination controls consistently (`page`, `page_size`) for all three resources.
